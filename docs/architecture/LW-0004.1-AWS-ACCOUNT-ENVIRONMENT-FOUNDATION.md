# LW-0004.1 --- AWS Account & Environment Foundation

## Purpose

Define the approved AWS account, environment, identity, data,
infrastructure, security, deployment, cost, and recovery boundaries for
LoanWise before application infrastructure is deployed.

## Approved Environment Model

```text
                         LOANWISE PLATFORM
                                │
                 ┌──────────────┴──────────────┐
                 │                             │
             DEV / POC                       PROD
                 │                             │
       Existing AWS Account             Dedicated AWS Account
                 │                             │
       Developer/Admin +              100 Students
       synthetic test user            1 Teacher
                                      2 Administrators
                 │                             │
          Synthetic Data                 Real Data
```

## DEV / POC

DEV/POC is a complete functional engineering environment, not a
disposable subset of the application.

It should contain production-representative application architecture
while remaining intentionally small in scale.

### DEV responsibilities

- Application development
- Proofs of concept
- Integration testing
- Security testing
- Terraform validation
- CI/CD validation
- Synthetic-data testing
- Infrastructure rebuild exercises
- Recovery procedure testing

### DEV rules

- No real customer data.
- No real customer credentials.
- No production secrets.
- Developer/admin access is allowed.
- Synthetic test identities are allowed.
- Infrastructure is disposable.
- Full rebuild from Terraform must be possible.

## PROD

PROD is the customer-facing environment and the authoritative location
for production data.

### PROD responsibilities

- Customer access
- Real application workloads
- Real customer data
- Production authentication and authorization
- Production monitoring and alerting
- Backup and recovery
- Security operations

### PROD rules

- Production data never enters DEV.
- Production changes use controlled deployment paths.
- Direct manual infrastructure changes are minimized.
- Production secrets are managed through approved secret-management
  mechanisms.
- Data-bearing resources receive explicit recovery/deletion
  protections.

## Identity Architecture

Human identities are separate from AWS infrastructure identities.

```text
Human Users
    │
    ▼
Cognito
    │
    ├── Student
    ├── Teacher
    └── Administrator

Developer / Operator
    │
    ▼
AWS IAM / approved administrative access

GitHub Actions
    │
    ▼
OIDC
    │
    ▼
Environment-specific deployment role

Lambda
    │
    ▼
Lambda execution role
```

Users authenticate through Cognito and are authorized by the
application. They do not receive broad AWS IAM permissions merely
because they use LoanWise.

## Terraform Boundary

The canonical infrastructure layout is:

```text
infrastructure/
├── bootstrap/
│   └── state/
├── environments/
│   ├── dev/
│   └── prod/
└── modules/
```

DEV and PROD state must remain isolated.

Production state must never be shared with DEV.

The account and environment identifiers should be supplied through
configuration rather than hardcoded throughout modules.

## Security Foundation

The production baseline includes:

- IAM least privilege
- Cognito
- KMS encryption
- Secrets Manager
- S3 Block Public Access
- CloudTrail
- CloudWatch
- AWS WAF
- GuardDuty
- Inspector
- Security Hub
- appropriate AWS Config controls
- backup and recovery controls

DEV should implement the security controls needed to make application
and infrastructure testing meaningful, while avoiding unnecessary
production-only operational overhead.

## Application Architecture Boundary

The initial application pattern is serverless:

```text
Internet
   │
   ▼
CloudFront
   │
   ├── S3 static frontend
   │
   └── API Gateway
          │
          ▼
        Lambda
          │
       ┌──┴─────────────┐
       ▼                ▼
   DynamoDB             S3
       │
       └── Secrets / KMS as required
```

The exact resource inventory will be finalized in later LW-0004 work
items.

## Cost Controls

Initial planning targets are:

- DEV: intentionally low usage and disposable infrastructure.
- PROD: approximately \$25--\$50/month at the initial expected
  workload, subject to actual AWS usage and selected security
  features.
- Budget alerts should be configured before production launch.
- Mandatory tags should identify application, environment, tenant, and
  Terraform ownership.

Example tag model:

```text
Application = LoanWiseMethod
Environment = dev | prod
Tenant      = loanwise
ManagedBy   = Terraform
```

## Disaster Recovery Strategy

### DEV rebuild test

DEV is expected to support complete infrastructure destruction and
reconstruction.

Acceptance flow:

1.  Confirm DEV contains only synthetic data.
2.  Destroy DEV infrastructure through the approved Terraform procedure.
3.  Confirm expected resources are absent.
4.  Reinitialize Terraform state.
5.  Recreate the environment.
6.  Redeploy the application.
7.  Recreate synthetic identities/data.
8.  Execute automated validation.
9.  Record rebuild duration and failures.

### Production recovery test

Production must never be casually destroyed as part of a DR exercise.

Instead:

1.  Protect production data with the approved backup/PITR/versioning
    mechanisms.
2.  Provision an isolated recovery target.
3.  Rebuild required infrastructure from Terraform.
4.  Restore a copy of production data into the recovery target.
5.  Restore required application configuration and secrets using
    approved procedures.
6.  Deploy the application.
7.  Validate authentication, authorization, application workflows,
    database integrity, document access, monitoring, and security
    controls.
8.  Measure actual RTO and RPO.
9.  Destroy the recovery target after validation.
10. Record findings and remediation actions.

### Data protection rule

> **Infrastructure is reproducible; production data is protected.**

Infrastructure recovery and data recovery are separate capabilities and
must be tested separately.

## RPO / RTO

Initial RPO and RTO values are requirements to be established before the
production backup architecture is finalized.

The DR test record must capture:

- Target RPO
- Actual RPO
- Target RTO
- Actual RTO
- Data restored
- Validation results
- Recovery failures
- Remediation actions

## Out of Scope for LW-0004.1

- Full application resource deployment
- Production user onboarding
- Final production DNS cutover
- Final backup implementation
- Full CI/CD implementation
- Final RPO/RTO values

Those are addressed by subsequent LW-0004 work items.
